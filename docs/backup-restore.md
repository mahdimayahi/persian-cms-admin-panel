# پشتیبان‌گیری و بازیابی (Backup / Restore)

این سند روند **قابل‌تکرار** پشتیبان‌گیری و بازیابی را مستند می‌کند. اسکریپت‌ها داخل مخزن‌اند و به هیچ مسیر محیطی خاصی وابسته نیستند.

---

## ۱) چگونه پشتیبان‌گیری می‌کنیم و چرا این روش؟

- **کل سیستم در یک فایل است:** `db/custom.db`. فایل‌های رسانه به‌صورت base64 **داخل خود پایگاه‌داده** ذخیره می‌شوند (ستون `Media.data`)؛ پس پشتیبانِ فایل دیتابیس = کل محتوا + کل رسانه‌ها، با سازگاری زمانی تضمین‌شده (همیشه هم‌زمان).
- **روش:** `VACUUM INTO` از اتصال فقط-خواندنی — یک snapshot تراکنشی کامل می‌سازد؛ منبع تغییر نمی‌کند و حتی در حین نوشتن سرویس، خروجی سازگار است. **کپی خام فایل `.db` در حال کار، روش مجاز پشتیبان‌گیری نیست** (حتی با journal_mode=delete، در حالت WAL هم کپی خام محتوای journal را از دست می‌دهد).
- **زمان‌بندی journal فعلی:** `delete` است. در صورت تغییر آینده به WAL، روش VACUUM INTO همچنان صحیح و کافی است و تغییری در اسکریپت لازم نیست.
- ابزار وابسته‌به-محیط لازم نیست؛ اسکریپت با زمان اجرای خود پروژه (Bun + ماژول داخلی `bun:sqlite`) کار می‌کند.

## ۲) اجرا

```bash
bun run db:backup                    # از دیتابیس پیش‌فرض (.env) به backups/
bun scripts/backup.ts --db <مسیر> --out <پوشه> --keep <N>
```

خروجی هر اجرا:
- `backups/cms_<زمان>.db` — فایل پشتیبان
- `backups/cms_<زمان>.manifest.json` — مانیفست برای راستی‌آزمایی بازیابی

### فهرست اقلام backup

| قلم | محل | توضیح |
| --- | --- | --- |
| محتوا و ساختار | `cms_<زمان>.db` | همهٔ جدول‌ها (کاربر، مقاله، رسانه‌ها و…) |
| رسانه‌ها | داخل همان فایل (`Media.data`) | فایل رسانهٔ مجزا وجود ندارد |
| نسخهٔ اسکیما | مانیفست → `table_columns` + `schema_file_sha256` | فهرست ستون‌های هر جدول + هش `prisma/schema.prisma` |
| نسخهٔ کد | مانیفست → `commit_sha` | SHA کامیت مخزن هنگام گرفتن پشتیبان |
| تنظیمات ضروری | مانیفست → `setting_keys` | **فقط نام کلیدها؛ مقادیر هرگز** در مانیفست ثبت نمی‌شوند |
| `.env` عملیاتی | **خارج از Git و خارج از مانیفست** | باید جداگانه (مثلاً `/var/backups` با دسترسی 600) نسخه‌برداری شود؛ حاوی مسیر دیتابیس است |

### قواعد
- پشتیبان‌ها **هرگز وارد Git نمی‌شوند** (`.gitignore` شامل `/backups/` است).
- نگهداری پیش‌فرض ۷ نسخهٔ آخر (`--keep`).
- مانیفست شامل `db_sha256` و نمونهٔ هش رسانه‌هاست — برای اثبات درستی بازیابی.

## ۳) بازیابی (فقط مسیر جدید)

```bash
bun scripts/restore.ts --from backups/cms_X.db --to /مسیر/جدید/restored.db
```

قواعد ایمنی:
- بازیابی روی «دادهٔ اصلی» ممنوع است — فقط مسیر جدید؛ بازنویسی صریح با `--force`.
- بازیابی در سرویس زنده ممنوع است: اول سرویس را متوقف کنید، فایل را جایگزین کنید، سرویس را روشن کنید (گام ۷.۴ `DEPLOYMENT.md`).
- پس از کپی، اسکریپت خودکار این‌ها را راستی‌آزمایی می‌کند:
  1. `PRAGMA integrity_check`
  2. `PRAGMA foreign_key_check` (صفر تخلف)
  3. شمارش سطر **همهٔ جدول‌ها** در برابر مانیفست
  4. فهرست ستون‌های هر جدول در برابر مانیفست (نسخهٔ اسکیما)
  5. هش SHA-256 نمونهٔ رسانه‌ها (تا ۵ مورد)
  6. برابری کلیدهای تنظیمات
- خروجی ناموفق → exit code 1.

### خطر از دست رفتن نوشته‌های پس از backup
بازیابی، وضعیت را به لحظهٔ پشتیبان برمی‌گرداند؛ **هر نوشته‌ای که پس از گرفتن پشتیبان ثبت شده از بین می‌رود** (شامل نشست‌های کاربران، مقالات تازه، رویدادهای Analytics). برای کمینه‌کردن این پنجره:
1. سرویس را متوقف کنید (توقف نوشتن).
2. در صورت امکان، یک پشتیبان تازه بگیرید — اما اگر عمداً به پشتیبان قدیمی‌تر برمی‌گردید، بازهٔ از‌دست‌رفت را ثبت کنید.
3. پس از بازیابی، پیش از روشن‌کردن سرویس، راستی‌آزمایی اسکریپت را ببینید.

## ۴) نتایج اندازه‌گیری‌شدهٔ واقعی (این نسخه)

| عملیات | اندازه | زمان واقعی |
| --- | --- | --- |
| Backup کامل (`db/custom.db`) | ۱٬۷۶۸ KB، ۳۹ جدول، ۴٬۰۰۸ سطر | snapshot: **۹ms** — کل: **۲۴ms** |
| بازیابی + ۴۵+ چک راستی‌آزمایی به مسیر جدید | همان | کپی: **۱ms** — کل: **۱۲ms** |
| بازیابی پشتیبان پیش‌ازارتقا (تمرین rollback) | ۶۰۸ KB، ۹ سطر | کل: **۶ms** + اسکیما و داده درست برگشت |

مقیاس این اندازه‌گیری‌ها دادهٔ نمونه/fixture است (۱٫۸MB). اهداف عملیاتی، جدا از این اندازه‌گیری‌ها تعریف می‌شوند:

- **RPO هدف:** با cron روزانه ≈ ۲۴ ساعت؛ با اجرای ساعتی ≈ ۱ ساعت؛ با رپلیکیشن پیوسته (Litestream) ≈ صفر. مقدار هدف از نتایج اندازه‌گیری‌شده مستقل است.
- **RTO هدف:** توقف سرویس + کپی فایل + راستی‌آزمایی + راه‌اندازی ≈ چند دقیقه برای مقیاس فعلی؛ برای دیتابیس‌های چند‌گیگابایتی زمان کپی و راستی‌آزمایی را قبل از تعهد RTO، یک‌بار روی همان مقیاس اندازه بگیرید.

## ۵) بازیابی دادهٔ واقعی

آزمون بازیابی این نسخه روی دادهٔ واقعیِ در دسترس (دیتابیس توسعه با دادهٔ seed) و fixture اجرا شد. **بازیابی «دادهٔ production واقعی» هنوز تأیید نشده است** — پس از نخستین استقرار واقعی، یک بازیابی آزمایشی کامل طبق همین سند اجرا و نتیجه ثبت شود.

## ۶) انتقال پشتیبان به بیرون سرور (الزامی در عملیات)

پشتیبان باید حداقل یک نسخهٔ بیرون از سرور داشته باشد (rsync/restic/borg/object storage — گام ۷.۳ `DEPLOYMENT.md`). `.env` عملیاتی هم جدا از Git ولی همیشه همراه پشتیبان نگه داشته شود؛ بدون آن بازیابی در سرور جدید مسیر دیتابیس را نخواهد داشت.
