# آمادگی انتشار (Release Readiness)

نسخهٔ مبنا: `e58e297` (گزارش بستن ریسک‌ها). این سند، وضعیت «تثبیت انتشار، staging و پذیرش نهایی» را ثبت می‌کند. **نسخهٔ نهایی واحد تحویل = کامیتِ حاوی این سند**؛ SHA دقیق با `git rev-parse HEAD` در گزارش تحویل همان کامیت ثبت می‌شود و SHA آزمایش‌شده و تحویلی یکی است.

---

## ۱) وضعیت نهایی

- **آزمون‌شده و تحویل‌شده روی یک SHA واحد** — هارنس + typecheck + lint + build ایزوله پس از کامیت نهایی دوباره اجرا شده‌اند (exit codeها در گزارش تحویل).
- تغییرات این مرحله فقط در این‌هاست: اسکریپت‌های `scripts/backup.ts` و `scripts/restore.ts` + دستورهای `db:backup`/`db:restore`، مستندات `docs/*`، بهداشت مخزن (untrack `.env`، track `.env.example`، ignore پشتیبان‌ها). **هیچ تغییر منطق برنامه، اسکیما یا UI انجام نشد.**

## ۲) خط مبنا و بررسی‌ها

| بررسی | دستور | نتیجه |
| --- | --- | --- |
| هارنس مخزن | `bun run test:harness` | ۵۰/۵۰ PASS — exit 0 |
| Typecheck | `bunx tsc --noEmit` | صفر خطا — exit 0 |
| Lint | `bun run lint` | exit 0 |
| Build ایزولهٔ production | `bun run build:isolated` | exit 0 |

## ۳) پشتیبان‌گیری/بازیابی — انجام شد (جزئیات: `docs/backup-restore.md`)

- backup با VACUUM INTO از اتصال فقط-خواندنی؛ منبع اثباتاً دست‌نخورده (`git status` روی DB پاک).
- بازیابی به مسیر جدید + ۴۵+ چک خودکار (integrity، FK، شمارش همهٔ جدول‌ها، ستون‌ها، هش رسانه‌ها) — سبز.
- زمان واقعی: snapshot ۹ms / بازیابی+راستی‌آزمایی ۱۲ms (مقیاس ۱٫۸MB دادهٔ نمونه).
- ⚠ بازیابی «دادهٔ production واقعی» هنوز تأیید نشده — پس از نخستین استقرار واقعی، یک‌بار آزمون شود.

## ۴) تغییر اسکیما و rollback

- از نسخهٔ مبنا فقط **یک ستون افزوده شده**: `PublishBundle.runOpId` (nullable، بدون پیش‌فرض) — تغییر additive؛ هیچ حذف/تغییر نوعی نیست.
- **آزمون ارتقای واقعی** (نه روی دیتابیس از‌قبل‌به‌روز): دیتابیس با اسکیمای قدیم ساخته + داده درج شد → `prisma db push` با اسکیمای جدید → ۱۴ چک (حفظ رکوردها، متن فارسی، nullability، ایندکس‌ها، یکتایی، FK، integrity) — همه سبز.
- **سازگاری کد قدیم با اسکیمای جدید**: کلاینت Prisma قدیم روی DB ارتقایافته — خواندن/نوشتن/ویرایش سبز → rollback کدِ تنها امن است.
- **تمرین rollback داده**: بازیابی پشتیبان پیش‌ازارتقا در مسیر جدید — اسکیما و داده درست برگشت.
- rollback کد و داده به‌صورت جدا در `docs/staging-and-rollback.md` مستند است.

## ۵) HTTPS و proxy واقعی

- **اجرا شد**: خروجی production (پورت ۳۳۱۱ فقط-localhost) پشت **Caddy واقعی** با **TLS واقعی** (گواهی self-signed محلی) — ریدایرکت 301 HTTP→HTTPS، کوکی `Secure; HttpOnly; SameSite=lax` روی TLS، جعل هدر از طریق proxy بی‌اثر (بازنویسی hop-۱)، lifecycle نشست (ورود/me/خروج→401)، backend مستقیم فقط 127.0.0.1.
- **مسدود محیطی (صریح):** گواهی با اعتبار عمومی (Let's Encrypt) نیازمند دامنهٔ عمومی و پورت‌های 80/443 است که در این sandbox در دسترس نیست؛ آزمون واقعی با LE پس از استقرار روی سرور واقعی الزامی است. شبیه‌سازی هدر معادل آزمون TLS واقعی تلقی نمی‌شود — آزمون این نسخه TLS واقعی بود؛ فقط «اعتبار عمومی گواهی» باقی است.

## ۶) پذیرش مرورگری VIEWER (روی خروجی production در staging)

- ورود VIEWER از طریق HTTPS واقعی → داشبورد/مقالات/رسانه بار شد؛ رسانه برای بیننده مجاز است (`media.view` — طبق طراحی، باگ نیست).
- کنترل‌های نوشتن مطابق طراحی غیرفعال/پنهان: تنظیمات — همهٔ ورودی‌ها و دکمهٔ ذخیره disabled؛ منوی عملیات مقاله برای بیننده خالی.
- تلاش مستقیم API نوشتن با نشست VIEWER: PUT تنظیمات ۴۰۳، ساخت/ویرایش/حذف مقاله ۴۰۳، PUBLISH ۴۰۳، آپلود رسانه ۴۰۳، ساخت کاربر ۴۰۳ — و **اثبات بی‌تغییری DB**: شمارش همهٔ جدول‌ها + مقادیر تنظیمات + مقالات دست‌نخورده؛ تنها تفاوت‌ها = رویدادهای LOGIN/LOGOUT و state راهنمای ورود (رفتار مجاز).
- فارسی/RTL/موبایل ۳۶۰px بدون overflow افقی؛ صفر خطای console؛ خروج سالم.

## ۷) خطاهای DB و ایمنی retry (بازبینی محدود — بدون تغییر)

- نگاشت تفکیک‌شده: P2002→409 تعارض واقعی؛ P2034→409+transient؛ P2024/P2028→503 transient؛ سایر→500 فقط در لاگ. P2028 «تعارض» تلقی نمی‌شود.
- علت (کد) در پاسخ و لاگ هردو حاضر — بدون افشای جزئیات حساس؛ پیام عمومی ۵۰۰ فقط «خطای غیرمنتظره».
- **هیچ retry خودکار در کلاینت وجود ندارد**؛ همهٔ retryها دستی‌اند (دکمهٔ کاربر) و عملیات تغییردهنده با گارد نسخه/CAS سمت سرور امن است؛ retry بسته هم state-aware (موفق‌ها SKIPPED).

## ۸) بهداشت اسرار

- اسکن الگوهای توکن/کلید در **فایل‌های tracked**: صفر تطابق.
- اسکن **تاریخچهٔ Git** (`git log --all -p`): صفر تطابق برای الگوهای توکن/URL اعتباردار.
- `.env` تاریخی در همهٔ کامیت‌ها فقط `DATABASE_URL` (مسیر فایل) — هیچ رازی هرگز کامیت نشده.
- در این مرحله: `.env` از Git خارج شد (untrack؛ فایل محلی می‌ماند) و `.env.example` با فقط-placeholder به مخزن اضافه شد؛ `backups/` و خروجی‌های موقت ignore شدند.
- **توکن push در remote URL محلی** (`.git/config`) ذخیره است — هرگز وارد تاریخچه نشد اما: چون امکان راستی‌آزمایی استفاده/دسترسی قبلی توکن وجود ندارد، **توصیه می‌شود پس از پایان کار، PAT را در GitHub rotate/ابطال کنید** (ادعای «ابطال شده» بدون تأیید واقعی نمی‌شود).
- محدودیت اسکن: الگوهای شناخته‌شده را جست‌وجو کرد؛ «نبود توکن در Git» بر «نبود آن در shell history/لاگ‌های خارج از این محیط» دلالت ندارد.

## ۹) موارد اجرا‌نشده / مسدود محیطی (صریح)

1. **گواهی با اعتبار عمومی (Let's Encrypt) و دامنهٔ عمومی** — نیازمند پورت 80/443 و DNS؛ در sandbox مقدور نیست → پس از استقرار واقعی آزمون شود.
2. **بازیابی دادهٔ production واقعی** — دادهٔ واقعی موجود نیست؛ روی دادهٔ نمونه اجرا شد.
3. **پایش‌گر uptime بیرونی** — زیرساخت بیرونی لازم دارد؛ پیکربندی پیشنهادی در `docs/operations.md`.
4. **بروزرسانی لاگ‌های سرویس عملیاتی واقعی (systemd)** — این محیط systemd ندارد؛ راهنما مستند شد، اجرای واقعی پس از استقرار.
5. محدودیت‌های فاز قبل (بار سنگین ۱۰۰+ نویسنده، تزریق خرابی زیرساختی در میانهٔ تراکنش، مکث worker با sleep واقعی) همچنان خارج از امکانات این محیط است.

## ۱۰) خطرهای باقی‌مانده و چک‌لیست پیش از انتشار عمومی

خطرهای باقی‌مانده (مدیریت‌شده، نه حذف‌شده):
- SQLite تک‌نویسنده است؛ رقابت شدید نوشتن → ۵۰۳ transient بیشتر می‌شود (رفتار امن، تجربهٔ کاربری محدود).
- رسانه در DB ذخیره می‌شود → رشد DB و اهمیت پایش دیسک و پیوست‌های خارجی پشتیبان.
- توکن push محلی در `.git/config` → پس از تحویل، rotate شود.

چک‌لیست کوتاه پیش از انتشار عمومی:
- [ ] تغییر همهٔ رمزهای فیکسچر (`prisma/seed.ts` و README) در استقرار واقعی
- [ ] `.env` با مسیر مطلق + دسترسی 600؛ هرگز وارد Git نمی‌شود
- [ ] HTTPS با گواهی معتبر + redirect آزموده شود (بند ۵)
- [ ] کرون `db:backup` روزانه + یک نسخه بیرون سرور + یک بازیابی آزمایشی کامل
- [ ] پایش‌گر uptime بیرونی فعال
- [ ] تگ انتشار با نام پیشنهادی فقط پس از تأیید شما ایجاد شود (بدون اجازه، tag منتشر نشد)

**پیشنهاد نام tag:** `v1.1.0-staging` (تغییر: بستن ریسک‌های concurrency/امنیت + هارنس + عملیات پشتیبان) — بدون اجازهٔ شما ساخته/منتشر نمی‌شود.

**وضعیت اعلامی: آمادهٔ staging.** برای «انتشار کنترل‌شده»، پیش‌شرط‌های بخش ۱۰ باید در محیط واقعی اجرا شوند؛ انتشار عمومی منتظر تأیید شماست.
